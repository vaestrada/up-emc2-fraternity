## 3. Bugs & issues (prioritized)

### HIGH — the "brods only" gate is not enforced

Today **any email** can sign in to `/portal` with a magic link (no password, no verification),
and the profile save does an `upsert` into `public.members` that its own-row RLS policy
(`using auth.uid() = id`) permits. So a stranger can sign in, claim an id, set
`visibility='brods'`, and appear in the private `/portal/directory`. The private directory is
logically gated but the door is open at signup.

Also, the master roster (`assets/docs/members_master.csv`, 490 people with birthdates,
addresses, phones, emergency contacts) is deliberately *not* imported — good — which means
the portal currently has **no way to verify someone is actually a brod**. Both halves of the
problem need fixing together. Full design in §5 (council is stress-testing it).

### HIGH — fictional people are on the public homepage

`lib/content.ts` carries 4 synthetic "prominent brods" (`synthetic: true`), 2 synthetic donor
quotes, and 5 demo gallery photos. The homepage renders `prominentBrods` directly, so the
public landing page currently shows "Engr. Marcus Andres Villareal" and three other **fictional
alumni** as if they were real citations, with only a small "Demo — AI-generated" corner badge.
Before public launch this must be gated behind an env flag or removed; for a board walkthrough
it is fine, but the board should explicitly know the public version must not ship with it.

### MEDIUM — (FIXED) middleware trims a Supabase auth call off every public page

The middleware ran `await supabase.auth.getUser()` on **every** non-static route (the public
site included), an extra network round-trip to Supabase on every page view at no benefit.
Narrowed the matcher to `/portal/:path*` and `/auth/:path*`. Build stays green.

### MEDIUM — (FIXED) auth-callback open-redirect hardening

`app/auth/callback/route.ts` took `?next=` and prepended `origin`, which could be coaxed into
a host-controlled redirect target. Now only same-origin relative paths are honoured. No
behavior change for the real flow (the client always sends `/portal`).

### MEDIUM — hero above-the-fold text waits on a JS reveal

The h1 wordmark, motto, and CTAs are `opacity: 0` until a framer-motion reveal fires.
First paint is near-empty and the LCP text is animation-gated. For an aging-alumni audience
and for Core Web Vitals, the hero's core content should be visible by default and only the
decoration/transform should animate. Worth a low-risk tweak.

### LOW — section numbering reads out of order on the homepage

The homepage presents sections in this order: `№ 01` Credo, `№ 02` Brotherhood, `№ 03` Ledger,
`№ 04` Citations, `№ 04½` Bulletin, `№ 06` The Next Quantum Leap, then `№ 05` Patronage.
So "06" appears above "05." For a "monumental, precise" brand, reorder so Patronage (05)
precedes Next (06), or renumber.

### LOW — deployment reliability (not code)

The Supabase project is on the free plan and auto-pauses after ~7 days. A paused DB makes
Vercel's resource-provisioning step fail, so a deploy dies in under a second with
`BUILD_FAILED: Resource provisioning failed` and no build logs (README documents this, twice).
Recommend: a deploy guard/alert or a scheduled warm-up so the demo build never silently fails.

## 4. Design review (from live screenshots + code)

The identity reads **dignified, monumental, and archival** — exactly the "engraved, learned,
quietly powerful" brief. You can see it in the hero: the deep green field, blueprint grid, a
faint rotating seal watermark, schematic corner annotations (`14.6553° N / 121.0685° E —
MELCHOR HALL, 3F LOBBY`, `EST. MCMLXIX`), a warm lamplight glow, and the duotone anniversary
group photo fading up into the canvas. CTA contrast is strong (gold "Give Back").

**The honest tension:** at first glance it reads more *somber museum / state archive* than
*proud brotherhood*. The hero photo is dimmed to ~25% opacity, the whole field is very dark,
and the gold is so restrained that a first-time visitor lands on "elegant and old" before
"we are alumni who are proud of each other." For a fraternity that wants to be recognized as
*fraternal* in five seconds, the recommendation (backed by the research agents, sources to be
cited in the full report) is to:

- **Let a person or two read as clearly brothers** — raise a warm, human photograph's
  presence (still archival, but not a near-silhouette), so the first eye-full is people, not
  just atmosphere.
- **Lift the wordmark legibility** — the hero title is the LCP; give it enough contrast and
  not-animation-gated visibility.
- **Reserve gold for what matters and make it land** — the mantra is already right; just make
  the single hero CTA and one honor badge pop so the eye has a destination.
- **Lead the alumnus journey** — an alumni-eyed visitor scans for "give back," "find a
  brother," "update my record," "who's honored." Surface those as the primary paths, not only
  in the nav.
- Keep everything else: the identity is a genuine strength and should not be rebuilt.

## 5. Brods-only portal — recommended architecture *(being stress-tested by the council)*

The goal: only verified members can reach their own record, the private directory, dues, and
(soon) member chat/content — while the PII roster never gets imported and RA 10173 is honoured.

**Direction (council refinement lands next):** stop letting the magic link create a member on
its own. Two halves:

1. **Membership is granted, not self-asserted.** A brod must be *verified* before they can
   enter. Realistic shapes, in rough order of preference:
   - *Invite-gated, board-verified:* the Association mints a one-time invite for a brod
     (offline from the roster, so PII never enters the DB); the brod claims it with their own
     email via the magic link. Supabase supports `auth.admin.inviteUserByEmail` and
     `signInWithOtp({ options: { shouldCreateUser: false } })` so only invited/pre-created
     emails can sign in. This is the cleanest "verified member only" guarantee.
   - *Claim + human approval:* the brod requests access with name/batch/email, a board member
     verifies against the roster (held offline), then activates. Friendlier for people who
     lost touch, slower.
   - *Custom access-token hook:* a Postgres/Edge auth hook that inspects the user's
     `app_metadata` (or a `members.verified` flag) and stamps a custom claim into the JWT;
     the portal pages + RLS then require `verified`. This is the enforcement layer that makes
     "brods only" a hard guarantee rather than a UI convention.
2. **Private by default, consent-controlled.** Already mostly there: `visibility` defaults
   `private`; only the member can touch their row; contact fields are hidden unless toggled.
   Extend so an unverified account can never read the directory at all, and so a member can
   exercise RA 10173 data-subject rights (access, correct, withdraw consent, request erasure)
   directly from their portal.

**RA 10173 (Philippine Data Privacy Act of 2012) checklist to bake in** (anchors confirmed by
research; full report cites the provisions): explicit lawful basis + informed consent at
signup; purpose limitation; data minimisation (collect only what serves the brotherhood);
data-subject rights (access/correction/erasure) surfaced in the portal; reasonable security
incident response and NPC breach notification; retention limits; and a DPIA consideration
given the directory holds extended PII. The site's existing stance — roster never imported,
per-member consent, private-by-default — is the right posture and should be kept.

## 7. Research findings — three agent deep-dives (sources as linked)

Three research agents ran against the GitHub/API, Supabase docs, RA 10173, and NN/g/W3C/Baymard. Key takeaways, honestly framed:

### 7a. The "fraternity website" skills landscape (agent 1)
- **There is no good fraternity-specific open-source website template.** The fraternity repos on GitHub are real but low-star hand-built chapter sites. The real ready-made value is in **framework-agnostic, anti-slop design skills**, plus using real fraternity/heritage repos as structural patterns.
- Best ready-made resources: Anthropic's official **`frontend-design`** (explicitly names the three "AI default" looks to avoid — incl. cream+terracotta-serif, near-black+acid-green, broadsheet-hairline), **`brand-guidelines`** (locks one institutional voice), **`canvas-design`**, and **`prompting_for_frontend_aesthetics.ipynb`** (their anti-slop checklist). Curators: **`awesome-agent-skills`** (32k★), **`awesome-design-skills`**, **`awesome-claude-design`**. Closest existing palette/type system: **`academic-website-template`** (370★, parchment + Source Serif 4 — borrow the *palette + type system + data-driven* pattern, it's Jekyll not your stack).
- **Best structural analogue to your build: `sigma-phi-delta-beta-nu/spdcalpoly.com`** — Sigma Phi Delta (a *professional engineering fraternity*) on Astro+Tailwind, with a data-driven `src/data/` (officers, pledge classes, brothers, site motto) and a **pledge-class lineage timeline** (Founding → line → current). That lineage tree is also the single strongest "unmistakably fraternity" trust device (see `nfischer/framily-tree`). Real heritage references: **Phi Beta Kappa** (founding-motto + founding-year masthead + one recurring emblem + "Accept your invitation" framing), **Royal Society** (lead with *owned scanned archives*, not stock), **Royal Institution** (a deep timeline band).
- 12 concrete React+Tailwind recommendations to sharpen the archive identity: an "index of the hall" nav (not pills, no backdrop-blur), one sacred line-art emblem, hero-as-thesis, an `ArchivePlate` component (rounded-none, hairline, Cormorant caption, "Plate XVII"), hairline grammar + zero radius, ledger/"rolls" tables instead of icon grids, the lineage/big-little tree, and a strict gold-as-single-accent palette. Codify in DESIGN.md so the identity survives edits.

### 7b. Making it read institutional *and fraternal* at first glance (agent 2)
- The first judgment is formed in ~**50 ms** (Lindgaard 2006) and rarely changes; NN/g says the four credibility levers are design quality, up-front disclosure, comprehensive/current content, and connection to the rest of the web.
- **Your dark palette is already exceptional**: cream-on-canvas is ~**14.84:1** (AAA). The two real hazards are **gold as body text** (~6:1, miss the 7:1 AAA an aging audience wants) and **gold-on-cream** (**2.45:1 — fails outright**). Keep gold as a scarce accent, never running copy, never on cream.
- The strongest verified color claim: *Journal of Consumer Research* "Color of Status" (7 studies) — **low saturation raises a luxury/heritage brand's perceived status**. Your muted brass + desaturated deep green is exactly right; **do not brighten it**.
- The fraternal lever is **named people, not effects**: a register of real brothers, batch names, named founders/officers, authentic photos of actual members, and an inside-out "we/us" voice. NN/g's own users said authentic images made it feel "like it's not about taking your money… you're going to be proud of it."
- "Monumental" and "cool" can collide — the resolution is **monumental-but-restrained**: impress through typographic scale, negative space, and precision, never motion/spectacle/decoration. (This is the one tension worth watching, given your cinematic scroll-video sections.)

### 7c. Brods-only portal + RA 10173 (agent 3) — the recommended design
- **Root cause confirmed in code:** `signInWithOtp` defaults to auto-creating the auth user, so any email gets in and, via the own-row `upsert`, can appear in the directory.
- **Recommendation:** a hash-only **member allowlist** (email-hash + batch, board-seeded from the roster offline, zero raw PII) as the harder gate; a **before-user-created hook** + **self-service sign-up disabled** + `signInWithOtp({shouldCreateUser:false})` so a stranger's email can never mint an account; and **deny-by-default RLS** driven by an `is_member` claim so even a token-holder with no valid claim can't read the directory. The **custom access-token hook** that injects `is_member` is *enrichment, not the gate* — the council's red-team lens correctly flagged that an access-token hook is documented to **fail open** (if it errors, Supabase still issues the token), so it must never be the sole deny control. A **human board/vouch escape hatch** survives for the rare edge case (changed email, lost access) — the board ratifies it, and two unverified strangers vouching must never auto-complete (removes the sybil vector).
- **Concrete plan:** new `portal_eligibility` (hash-only) table, an `is_member()` security-definer helper, rewritten RLS policies requiring `is_member() and verification_status='approved'` for edit/browse; `signInWithOtp({ options: { shouldCreateUser: false } })`; disable self-service sign-up; a service-role `claimInvite` server action; a private-by-default + explicit, versioned `consent_listed` field; an access audit log.
- **RA 10173 mapped to concrete decisions:** explicit lawful basis + consent (directory listing = explicit, timed consent), purpose limitation, data minimisation (no birthdate/address/phone/emergency contact ever enters the portal DB), data-subject rights (access/correction/erasure surfaced in the portal), security (RLS everywhere, service-role writes, hashed tokens), a **DPO**, a **breach runbook** (NPC Circular 16-03 puts **72 hours** on the NPC notification), retention limits, and **a DPIA is warranted**. NPC registration threshold: with ~490 members you don't cross the 1,000-person sensitive-PI line, but registration is still recommended if processing is regular/risky — confirm with the NPC whether the association is already registered for its legacy database.
- **Consistency with your privacy stance:** this is *stricter* than PRIVACY.md rule 4 today ("import the CSV into a RLS table"). Recommend rewriting rule 4 to: *roster data is never imported; access is via offline-minted one-time tokens / a hash-only allow-list; delete local copies after each mint.*
- **Marked unverified (validate before shipping):** the exact JSON payload field names for the two auth hooks (Supabase's current template is the authority), whether an officers/admin-role table already exists, whether a Supabase data-processing addendum is executed, the exact current NPC circular making a DPIA mandatory, and the Auth rate-limits dashboard path/labels.

### 7d. Two honest tensions to decide
1. **Cinematic scroll-video vs. "monumental, not an event page."** NN/g and the research flag autoplay/looping video as the single most *startup* signal and an LCP risk. Your recent work added ScrollCinematic showcase videos; they're genuinely crafted, but they lean "wow-reel." Decide whether to keep them as a quiet, non-autoplay, reduced-motion-safe accent or lean fully "static hall." Not something to silently rip out.
2. **Public "find a brother" vs. private-by-default.** Practitioner guidance says alumni directories should be browseable reconnect tools; RA 10173 + your PRIVACY stance says the directory is login-gated and default-private. The workable synthesis: the **names-only register** can be a browseable public list of members who opt into `visibility='public'`, but contact details and the full directory stay consent-gated and brods-only. Keep the consent-first posture; it is the stronger and safer one.

### 7e. Council verdict — blind, five lenses (26 Aug)

The five lenses were not the same answer, and that's the useful part.

- **Every lens agreed** on the baseline: deny by default at the auth boundary. `signInWithOtp({ shouldCreateUser: false })`, self-service sign-up turned off, and RLS as the real lock. The pragmatist's sharpest point: ship these **as one unit** — `shouldCreateUser:false` alone locks everyone out (no auth users exist yet), and removing the profile-insert path alone still lets a stranger mint an account; only the pair plus a seeded allowlist closes the hole *and* stays demoable.
- **The real split** is how to verify membership, because the roster is never imported and email control is not proof of brotherhood. First-principles put it precisely: identity is three decoupled layers — *authentication* (email possession, weak), *membership* (an attestation only the organization can make), *verification* (a trusted human or chain of verified members attesting it). So a magic link alone must never be enough; **a human is necessarily in the loop** for the rare case of a member the system can't pre-confirm.
- **The red-team lens forced a correction I've accepted:** a **custom access-token hook fails open** (if it errors, Supabase still issues the token and logs a warning), so it can only *enrich* the JWT, never *deny*. The deny control must live at the auth boundary (before-user-created hook / disabled sign-up / `shouldCreateUser:false`) and in **deny-by-default RLS**, not in the hook. It also correctly knocked the "email a one-time invite token" idea: a token is a possession proof, not a verification — it leaks by forwarding, screenshots, and group DMs.
- **Chairman synthesis:** a **hash-only member allowlist** (email-hash + batch), board-seeded from the roster *offline* so zero raw PII enters the DB, is the primary hard gate. The board pre-creates (via `auth.admin.createUser`) a first cohort so the member path works and the stranger path is blocked for the demo. The `before-user-created` hook + disabled sign-up + `shouldCreateUser:false` deny all non-allowlisted emails; the access-token hook just stamps `is_member` for RLS convenience; deny-by-default RLS is the lock. A **small, hard human "vouch + board confirm"** path remains only as the escape hatch for changed/lost access — and two unverified strangers vouching for each other must never auto-approve.
- **Honest caveats to validate against the live Supabase project before wiring it up:** the exact `event`/payload keys for the two auth hooks (Supabase's current templates are the authority); whether `admin.createUser` bypasses `before-user-created`; whether the app already has an officers/admin-role table for the guardian step; and the Auth dashboard's rate-limit/sentinel labels. `shouldCreateUser:false` also leaks email *existence* via error code and timing — acceptable for fraternities, worth knowing.
